Cross-database work, without the guesswork.

Built for developers, DBAs, and data engineers who juggle more than one database engine. Each workflow below works on its own—and together they take you from exploring an unfamiliar schema to rewriting SQL and executing a reviewed migration.

Schemas and queries, side by side.

Keep connections, databases, schemas, and objects in one unified tree. Click any table to inspect its DDL and indexes, then open a query tab right beside it—complete with schema-aware completion, inline syntax checks before execution, symbol rename, and incremental pagination for large result sets.

  • Table and view DDL for 12 SQL engines, plus dedicated catalog views for MongoDB, Redis, and Elasticsearch
  • Single queries stream page by page; paging and CSV export reuse cached results without running your SQL again
  • Catch draft syntax issues inline, with server-enforced confirmation before destructive statements like DELETE, UPDATE without WHERE, or column type changes

Rewrite SQL and see every change.

Translate SQL across 10 dialects—including PostgreSQL, MySQL, SQL Server, Snowflake, Oracle, and DuckDB. Compare source and output side by side to spot rewritten functions, quoting changes, and structural diffs, while column lineage traces every output column through CTEs, subqueries, JOINs, and UNIONs.

  • Powered by a local Rust parser—nothing is executed and no database connection is required
  • Unsupported target-dialect constructs and unresolved lineage are flagged explicitly instead of silently dropped

Review the preflight before you move.

Pick a source, a target, and the tables to copy—dbfox runs a read-only preflight first. Every column mapping is graded as L1 lossless, L2 lossy, or L3 unmappable, with target conflicts flagged up front. Nothing is written until you explicitly decide how to handle lossy and unmappable items.

  • Copies tables, primary keys, indexes, unique constraints, and rows, then verifies row counts table by table
  • Unmigrated objects—such as views, foreign keys, and triggers—are listed clearly in the plan; export plans and reports as JSON or Markdown

Up and running in three steps

  1. Add a connection

    Click New connection and choose your engine—or paste a connection string or key-value details to auto-fill the form. Start with a read-only account.

  2. Inspect a table

    Expand the object tree and click any table to view its DDL and indexes, or choose Preview data (LIMIT 100) from its menu.

  3. Try it without a database

    Open SQL Conversion in the top bar—no connection needed. Paste any query, pick two dialects, and inspect the diff and column lineage right away.

Good to know before you start

Do I need a dbfox cloud account?

No. dbfox runs locally on your machine and connects directly with your own database credentials—nothing routes through a dbfox cloud service. Connection profiles are stored in a local data directory with encrypted passwords (the encryption key sits alongside them, so protect that directory as you would credentials). If you attach an external AI assistant, its own account and data-handling policies apply.

Can I run queries on all 15 databases?

Execution depends on the engine: 12 SQL engines (PostgreSQL, MySQL, MariaDB, SQL Server, SQLite, Snowflake, DuckDB, DuckLake, Oracle, Db2, Redshift, and ClickHouse) run SQL; Elasticsearch accepts read-only SQL and GET / _search / _count requests; MongoDB and Redis execute native commands, including writes permitted by your database account. Cancelling a running query does not roll back statements that have already committed.

Does migration guarantee identical results across engines?

No. Database engines differ in types and constraint semantics, and views, foreign keys, triggers, and similar objects are outside the migration scope. dbfox performs a one-shot schema and data copy—not real-time CDC or zero-downtime replication. Always review preflight mappings and warnings, validate on non-production data first, and verify the final report.

Can an AI assistant modify or delete data through MCP?

No. All 15 MCP tools are strictly read-only—covering schema discovery, bounded read-only queries, SQL validation/conversion, and migration proposals—with no write or migration-execution tools. Read-only queries pass an AST check and execute inside rolled-back read-only transactions (supported on PostgreSQL, MySQL, MariaDB, SQL Server, and SQLite; not available for Snowflake or Elasticsearch). You can also disable agent access per connection and enforce least-privilege read-only roles in your database.

Are macOS and Linux builds available?

The desktop installer is currently Windows x64 only. On Linux, the Docker Compose bundle (linux/amd64 images) runs the exact same workspace in a desktop browser. macOS and Linux desktop installers are not yet available.
